## 2026-05-13 | 数据源策略：TMDB + 豆瓣混合

- **决策内容：** 以 TMDB API 作为主数据源获取全量电影元数据（片名、海报、简介、类型、上映日期、演员等）；豆瓣作为补充数据源，按需爬取评分和评论。
- **理由：** TMDB API 合法稳定、覆盖全量电影、支持中文片名；豆瓣无公开 API，无法爬取全量数据，但评分和评论对中文用户有重要参考价值。
- **替代方案：** 纯豆瓣爬虫（数据不全、易被封）；纯 TMDB（缺少中文评分参考）
- **影响范围：** 数据层架构需兼容两个数据源，需设计数据合并策略

## 2026-05-13 | 推送策略：双向推送

- **决策内容：** 两种推送模式并存——（1）新电影上线时根据用户匹配类型推送；（2）定时推送已上线电影。推送频率由用户自调。推送渠道初期为邮件，后期扩展至短信。
- **理由：** 新片推送满足即时性需求，定时推送保证持续触达；用户自调频率避免打扰；邮件低成本验证，短信后续扩展。
- **替代方案：** 仅定时推送（缺乏新片时效性）；仅新片推送（低频用户易流失）
- **影响范围：** 推送模块需支持多种触发模式，用户配置存储需包含推送频率字段

## 2026-05-13 | 注册策略

- **决策内容：** 注册支持邮箱和手机号两种方式；注册时可选择电影类型偏好，也可跳过。若跳过，推荐位置会引导用户选择类型。
- **理由：** 降低注册门槛，同时收集偏好数据以改善初期推荐效果。
- **替代方案：** 强制选择类型（增加注册流失率）；注册后完全不收集（冷启动推荐质量差）
- **影响范围：** 用户模型设计包含偏好字段，且需处理"未设偏好"状态

## 2026-05-13 | 网站功能范围

- **决策内容：** 仅 Web 端，无移动端；无管理后台；无需反馈机制。网站功能包括：注册/登录、首页推荐流（分页）、电影搜索筛选、电影详情页、历史推荐记录页、设置页。
- **理由：** MVP 阶段聚焦核心体验，减少非必要功能开发量。
- **替代方案：** 做后台/移动端/反馈机制（超出 MVP 范围）
- **影响范围：** 前后端功能清单据此确定，无管理后台意味着初期电影数据同步需手动或脚本处理

## 2026-05-13 | 用户访问策略：非登录可浏览

- **决策内容：** 非登录用户可浏览电影列表、详情页等内容；登录后获得个性化推荐和推送服务。
- **理由：** 降低使用门槛，同时使网站内容对搜索引擎可见，有利于 SEO。
- **替代方案：** 全站必须登录（内容对爬虫不可见，不利于传播）
- **影响范围：** 前端需支持 SSR（SEO 友好），故选择 Next.js；后端 API 需区分"公开接口"和"登录接口"

## 2026-05-13 | 后端技术栈：Spring Boot + Maven + MySQL + MyBatis-Plus

- **决策内容：**
  - 后端框架：Spring Boot
  - 构建工具：Maven
  - 数据库：MySQL
  - ORM：MyBatis + MyBatis-Plus
  - 定时任务：XXL-Job
  - 数据源调用：Spring RestClient（TMDB API）+ Jsoup（豆瓣爬虫）
- **理由：** Java 技术栈成熟稳定，用户熟悉度高；Spring Boot 生态完善、社区活跃；Maven 稳定可靠、资料丰富；MyBatis-Plus 开发效率高；XXL-Job 分布式调度成熟适合定时推送。
- **替代方案：** Gradle（学习成本较高）；PostgreSQL（用户更熟悉 MySQL）；JPA/Hibernate（MyBatis 更灵活）；Quartz/Spring Scheduling（XXL-Job 有管理界面更便于运维）
- **影响范围：** 所有后端开发工作基于此技术栈展开

## 2026-05-13 | 前端技术栈：Next.js + React

- **决策内容：** 前端使用 Next.js（React 框架），支持 SSR / SEO，前后端分离部署。
- **理由：** Next.js 支持 SSR 满足 SEO 需求；React 生态最大、第三方库最多、人才池最广；前后端分离有利于职责清晰和后续扩展。
- **替代方案：** Nuxt（Vue）Vue 生态稍小；Thymeleaf + Htmx（前后端合一，前端扩展性受限）
- **影响范围：** 前端独立为一个 Next.js 项目，通过 REST API 与后端通信

## 2026-05-13 | 冷启动策略：无画像时默认热门推荐

- **决策内容：** 用户不设置偏好时，默认推荐近期热门 + 高评分电影，而非随机推荐。
- **理由：** 随机推荐体验差（可能推荐烂片导致用户流失）；热门高评分是稳妥的冷启动策略，可覆盖未设置偏好的用户和游客。
- **替代方案：** 随机推荐（质量不可控）；直接展示所有电影（无排序，体验差）
- **影响范围：** 推荐模块需实现"热门精选"兜底逻辑；首页需区分"个性化推荐"和"热门推荐"两种展示模式

## 2026-05-14 | 预设画像 + 规则匹配替换"选电影+LLM"

- **决策内容：** 废弃"选 3-5 部电影 + LLM 分析"方案，改为预设画像方案。用户注册时从一组有名称、描述和示例电影的画像中选择（可多选）。推荐引擎基于画像规则匹配电影（类型、地区、预算、导演等维度），不再依赖 LLM 做推荐决策。LLM 仅用于为已推荐的电影生成个性化推荐理由文案，作为辅助层。
- **理由：** 预设画像比搜电影更直观、零延迟、注册门槛更低；规则匹配推荐引擎确定性强、可迭代、无额外成本；LLM 退出核心路径降低了延迟和费用风险。
- **替代方案：** 选电影 + LLM（有延迟和成本，画像质量依赖模型）；纯标签勾选（抽象不直观）
- **影响范围：**
  - 前端注册页改为"画像卡"选择界面，无需电影搜索组件
  - 后端去除 LLM 推理流水线，推荐逻辑改为规则引擎
  - LLM 降级为异步辅助：仅生成推荐理由文案
  - 多画像 Phase 1 即支持（原定 Phase 2）

## 2026-05-14 | 推荐引擎方案：本地数据 + SQL 规则匹配

- **决策内容：** 全量同步 TMDB 电影数据到本地 MySQL，推荐引擎通过 SQL 查询本地数据匹配画像规则。不使用 TMDB Discover API 做实时筛选。
- **理由：** 不受 TMDB 频率限制；支持复杂的条件分组逻辑（AND/OR 组合）；推荐可离线 batch 执行；数据可自由与豆瓣评分等本地数据关联。
- **替代方案：** 实时调 TMDB Discover API（受频率限制，无法做复杂条件分组）
- **影响范围：** 确认了数据同步方向，movie 表需覆盖 TMDB 所有可能用到的字段

## 2026-05-14 | 多用户画像提前至 Phase 1

- **决策内容：** 多画像功能从 Phase 2 提前到 Phase 1，支持用户选择多个画像。推荐时明确标注推荐来自哪个画像。
- **理由：** 预设画像方案天然适合多选（点选即可），无需额外复杂逻辑；多画像能显著提升推荐丰富度；用户选择画像时多选比单选更自然。
- **替代方案：** 保持 Phase 2（浪费了预设画像方案的优势）
- **影响范围：** user_profile 表需支持一对多；推荐结果需携带画像 ID 供前端展示"来自哪个人设"

## 2026-05-13 | 详细版本与配置确认

- **决策内容：**
  - Java 17 + Spring Boot 3.4.x
  - Node.js 20 LTS
  - Next.js App Router（而非 Pages Router）
  - Tailwind CSS（CSS 方案）
  - MySQL 8.0+
  - 不使用数据迁移工具，手动维护 SQL 脚本
- **理由：** 全选当前主流稳定版本；App Router 是 Next.js 官方推荐；Tailwind 与 Next.js 集成最佳；手动 SQL 脚本适合 MVP 阶段，不增加额外工具学习成本。
- **替代方案：** Pages Router（遗留方式）；CSS Modules（不如 Tailwind 高效）；Flyway/Liquibase（增加复杂度，MVP 阶段不必要）
- **影响范围：** 所有配置文件中的版本号依此确定
